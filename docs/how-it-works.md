# How the kiosk agent works

Everything that runs on a screen box, in detail: the display loop, the health
watchdog, the fleet agent, WiFi handling, updates and the security model.
Written against agent **v2.3**. For install steps see `manual-install.md`; for
the one-line installer see the README.

## 1. Big picture

```
┌─────────────────────┐   HTTPS (poll every 15s,        ┌──────────────────────┐
│  Display Manager    │   bearer token per screen)      │  Screen box (Ubuntu) │
│  (DSM web app)      │◄────────────────────────────────┤  kiosk-agent (root)  │
│                     │   SSH (instant-sync trigger,    │        │ writes      │
│  grid config, NVR   ├────────────────────────────────►│        ▼             │
│  details, WiFi,     │   forced command only)          │  /etc/kiosk/         │
│  SSH keys, commands │                                 │    config.json       │
└─────────────────────┘                                 │        │ read        │
                                                        │        ▼             │
┌─────────────────────┐   RTSP over TCP                 │  cams.sh (kiosk user │
│  Dahua NVR(s)       │◄────────────────────────────────┤  inside X on tty1):  │
│  one connection     │   one player per tile           │  N × mpv + watchdog  │
│  per tile           │                                 └──────────────────────┘
└─────────────────────┘
```

Two independent loops share one file:

- **`kiosk-agent`** (root, systemd) talks to the manager and maintains
  `/etc/kiosk/config.json`. The manager being unreachable never affects the
  running display.
- **`cams.sh`** (the kiosk user, inside X) turns that file into a wall of mpv
  players and keeps them healthy. It never talks to the manager.

The agent nudges the display by killing mpv (`pkill -x mpv`); the display loop
also polls the config file itself, so the nudge is a speed-up, not a
requirement.

## 2. Boot chain

1. systemd starts **`kiosk-display.service`** on tty1 as the kiosk user:
   `startx /etc/kiosk/cams.sh -- :0 vt1 -keeptty -nocursor`. It waits for
   `network-online.target` first (with the `--any` override, seconds — see §7)
   so players never start against a half-up network. `Restart=always`: if X
   itself dies, the whole session comes back.
2. systemd starts **`kiosk-agent.service`** (root, `Restart=always`).
3. systemd starts **`kiosk-wifi-watchdog.service`** (see §7).
4. `/etc/X11/Xwrapper.config` (`allowed_users=anybody`,
   `needs_root_rights=yes`) is what lets X start from a service on Ubuntu
   Server; `getty@tty1` is disabled so nothing fights over the console.

## 4. The display loop (`cams.sh`)

### Config shape

```json
{ "gridCols": 3, "gridRows": 2, "subtype": 1,
  "rotate": "none", "rotateOutput": null,
  "wifiSsid": null, "wifiPassword": null,
  "tiles": [ { "pos": 0, "ip": "10.66.2.66", "port": 554,
               "user": "dsm", "pass": "...", "channel": 1, "subtype": 0,
               "url": "rtsp://dsm:pw@relay:8554/nvr1-ch1-sub0" } ] }
```

- Grid up to 6×6. `pos` is row-major (0 = top-left); positions without a tile
  stay black. Tiles may come from different NVRs.
- `subtype`: 0 = main stream, 1 = substream. The per-tile value overrides the
  top-level default; tiles without one inherit it.
- Direct stream URL per tile:
  `rtsp://user:pass@ip:port/cam/realmonitor?channel=N&subtype=S`
  (password URL-encoded; Dahua path).
- `url` (v2.6+): the PREFERRED source — the manager's RTSP relay (MediaMTX on
  the manager host), which holds **one** upstream NVR session per camera and
  fans it out to every screen watching it (NVR session/bandwidth limits made
  direct per-tile streams lag once the fleet grew). The direct fields above
  always remain the fallback: a tile plays the relay when it answers, drops
  to the NVR when it doesn't (spawn probe, or in-place `loadfile` switch),
  and switches back — in place, no teardown — when the relay recovers
  (re-tried every 10 min; a switchback that fails within a minute backs off
  for 30 min). Agents older than v2.6 ignore `url` entirely.
- Broken tiles (missing ip/user/pass, bad channel) are skipped with a log —
  one bad tile never holds the rest of the wall hostage.

### One mpv per tile

Each tile is its own mpv process in a borderless window exactly covering its
grid cell (`--geometry=WxH+X+Y`, no window manager needed; cell sizes are the
screen divided by the grid, the last row/column absorbing rounding so the wall
reaches the screen edges). Rotation is applied first via `xrandr`, then the
screen is measured, so portrait screens lay out correctly.

Why per-tile processes (v1.9; before that one mpv composited everything
through an `hstack/vstack` filter graph): the graph waits on **every** input,
so one stalled camera froze the entire wall, and any recovery meant
restarting everything. With per-tile players a sick camera only ever disturbs
its own cell, and each cell can be restarted invisibly to the rest.

### The mpv flags and why each one is there

| Flag | Why |
|---|---|
| `--rtsp-transport=tcp` | UDP loses packets on busy networks → smearing; TCP doesn't |
| `--demuxer-lavf-o-add=fflags=+discardcorrupt` | drop packets the demuxer knows are damaged rather than render them |
| `--vd-lavc-o-add=err_detect=+crccheck+bitstream+buffer` | detect decode errors. Deliberately **not** `+explode`: that made decode errors fatal and left mpv alive with a black window and no clock (the v1.9 "tile stays black until reboot" bug) |
| `--keep-open=yes --idle=yes` | when the stream dies, mpv does **not** exit — it holds the last frame and waits; the supervisor reloads in place (see below). An outage looks like a paused picture, never a black cell |
| `--network-timeout=15` | a fully dead connection errors out within ~15 s instead of hanging forever |
| `--cache=yes --cache-secs=10 --demuxer-max-bytes=8M` | small cache absorbs network/CPU hiccups; `cache-secs` bounds how far behind live a tile can drift (~10 s worst case — the 8M byte cap alone allowed 30–60 s at substream bitrates) |
| `--no-audio --video-latency-hacks=yes` | walls don't play audio; both trim fixed pipeline latency |
| `--force-window=immediate` | the cell appears (black) instantly while the RTSP handshake runs |
| `--hwdec=auto` | VAAPI (i965) hardware decode where available |
| `--no-border --no-keepaspect` | fill the cell exactly |
| `--msg-level=all=error` | real errors reach the journal so a sick stream is diagnosable |

### Per-tile respawn loop (`tile_loop`)

Each tile runs a tiny loop: probe the NVR with a 3-second TCP connect
(`/dev/tcp`), spawn mpv if reachable, wait for it to exit, respawn after a
2–4 s stagger (staggered per position so several tiles never hammer a weak
link simultaneously). If the NVR is unreachable, the cell shows black and the
probe retries every 15 s. The mpv pid goes into a pidfile that is **removed
the moment the player exits**, so the watchdog can never kill a stale pid; it
also validates the pid against `/proc/<pid>/comm == mpv` before killing.

### The supervisor / watchdog

The main script becomes the supervisor once the wall is up. Every 5 s
(`WATCH_INTERVAL`) it:

1. **Config check** — md5 of `config.json`; on change, tear down all tiles and
   rebuild the wall. This is why the agent's `pkill mpv` is only a speed-up.
2. **Loop check** — a tile whose respawn loop died is respawned.
3. **Health check** — one IPC round-trip per player fetches six properties:
   `time-pos` (playback clock), `demuxer-cache-time` (is data arriving),
   `eof-reached`, `idle-active`, `demuxer-cache-duration` (how far behind
   live), `speed`.

The policy is "recover with the least visible disruption that actually
helps". History taught us the failure modes must be told apart — v2.0 used
one hammer (any 30 s clock stall → restart) and on flaky WiFi it killed
players that were mid-buffer and about to resume by themselves:

| Player state | Meaning | Action |
|---|---|---|
| clock advancing | healthy | nothing |
| EOF / idle (last frame or black held) | stream ended, connection died, or load failed | **reload in place** over IPC (`loadfile <url> replace`) as soon as the current source's host answers a TCP probe, retried every 15 s — the window never tears down, the picture pauses then resumes. If the tile is on the relay, a dead relay host or a relay stream that gets nowhere for 180 s switches the tile to the **direct NVR stream in place** instead of restarting. Otherwise, give up and restart the process only after 180 s of *reachable* reload attempts going nowhere (the give-up clock does not tick while the host is down, so post-outage recovery is always a seamless reload) |
| clock stuck, data still arriving | wedged decoder | restart that tile after 30 s (`FREEZE_SECS`) — nothing else fixes it |
| clock stuck, no data arriving | network starvation | leave it — mpv is showing the last frame and resumes by itself; restart only after 180 s (`STARVE_SECS`) as a last resort, because killing a buffering player trades a frozen frame for a black cell |
| no clock at all for 30 s | black window that never started | restart — there is nothing on screen to preserve |

NVR reachability is probed at most once per NVR per sweep (tiles usually
share an NVR). If `python3` is missing the health checks are disabled with a
logged warning; config reload still works.

**Latency governor.** Every stall (buffering pause, brief starvation) leaves
a backlog in the demuxer cache, and timed playback at 1× carries that backlog
forever — tiles used to drift 20–40 s behind realtime and stay there. The
supervisor watches `demuxer-cache-duration`: a healthy tile more than 2 s
behind live is played at 2× (`set_property speed 2` over IPC — a brief,
barely visible fast-forward) until it is within 0.5 s, then restored to 1×.
Combined with `cache-secs=10`, worst-case drift is ~10 s and it self-heals in
seconds.

**Main-stream degrade (v2.7).** A main-stream tile in a grid should soften,
never cut out: when a tile *provably* cannot sustain its main stream, the
supervisor drops that one tile to the **substream twin of the same camera**
(relay path `-sub0`→`-sub1`, direct URL `subtype=0`→`subtype=1`) — in place,
no teardown — and retries the main stream every 30 min. Two triggers:
- **lag-stuck**: >2 s behind live continuously for 120 s even at 2× — the
  box's decode budget (these units have no H.265 hardware decoding, so H.265
  mains are software-decoded) or the link can't keep up;
- **churn**: 3 watchdog restarts/give-ups without a 10-min healthy run in
  between.
The `.degraded` marker file makes player respawns honour the state; the full
relay/direct failover ladder keeps working on the substream twins while
degraded. Journal lines name the tile, the trigger and the retry cadence.
Estate note: setting a camera's **main stream to H.264** on the NVR lets
these boxes hardware-decode it, which is what makes main-in-grid genuinely
sustainable on wired screens (trade-off: H.264 recordings need ~30-50% more
NVR storage for the same quality).

### Logging

X swallows its clients' stderr, so the loop logs via `logger -t kiosk-cams`.
Read with `journalctl -t kiosk-cams -f`. Messages you'll see:

| Message | Meaning |
|---|---|
| `wall up (N tile player(s))` | build complete |
| `config changed - rebuilding the wall` | new config picked up |
| `tile N: stream ended - reloading in place (picture holds, no teardown)` | normal recovery from a drop |
| `tile N: NVR ip:port unreachable - black cell, retrying in 15s` | probe failing before spawn |
| `tile N: clock stuck ... (wedged player) - restarting` | hard failure, single-tile restart |
| `tile N: no stream data for Ns - restarting` | starvation last-resort (rare; means a long dead-but-connected stall) |
| `tile N: reloads got nowhere for Ns - restarting` | EOF give-up (NVR answers TCP but streaming keeps failing) |
| `tile N: player exited - respawning` | mpv process actually died (crash or kill) |
| `tile N: respawn loop died - restarting it` | supervisor self-healing its own plumbing |

## 5. The fleet agent (`kiosk-agent`)

Runs as root, ticks every 15 s (`POLL_INTERVAL`). Each tick:

1. **Route-flip check** — streams are TCP-bound to the source address of the
   interface they started on; when the default route moves (cable pulled →
   WiFi takes over, or back), those connections are dead. The agent detects
   the flip by watching the default route's device and immediately
   `pkill -x mpv` so every tile reconnects over the now-active path.
2. **Register** if there is no `API_TOKEN` yet: POST
   `/api/agent/register` with the enroll token, hostname, machine-id, agent
   version. The manager answers with a per-screen bearer token + screen id,
   appended to `agent.env`. A 401 on any later poll deletes the token and
   re-registers next tick.
3. **Poll** — POST `/api/agent/poll` with status (applied config/keys
   versions, agent version, display service active, local IP, uptime). The
   response carries the *desired* versions and any queued commands.
4. **Config drift** — if the desired config version differs from
   `applied-config-version`: GET `/api/agent/config`, validate the payload
   (grid bounds, at least one tile) — an invalid payload is ignored, never
   applied — install as `config.json` (root:kiosk 640), apply fleet WiFi if
   present (see §7), `pkill mpv`, record the version. X keeps running: new
   video in a few seconds, no black flash.
5. **SSH keys drift** — GET the key list, apply via
   `kiosk-update-ssh-keys`, which rewrites only its managed marker block in
   the kiosk user's `authorized_keys` and **refuses an empty list** (lockout
   safety). A refused version is remembered so it isn't retried until the
   list actually changes.
6. **Manager key drift** — installs the manager's public key into the kiosk
   user's `authorized_keys` as
   `restrict,command="sudo /usr/local/sbin/kiosk-trigger" <key>`.
7. **Commands** — executes queued commands and acks each
   (`restart-display`, `reboot`, `update-agent`, `wol:<mac>`; unknown types
   are acked as errors). Reboot acks first, then reboots detached so the ack
   isn't killed mid-flight.
8. **Power schedule** (v2.8, FB-0176) — `config.json` may carry a `power`
   block (`sleepTime`/`wakeTime` as `HH:MM`, `daysMask` bit N = day-of-week
   with Sunday=0, marking the days the screen *wakes* — sleep fires daily,
   so a Mon–Fri mask sleeps Friday evening through Monday morning). Times
   are **wall-clock in `power.timeZone`** (default `Europe/London`), not the
   box's own clock: the boxes run on UTC, which made v2.8 fire an hour late
   during BST — v2.9 routes every wall-clock computation through the
   schedule's zone. At the sleep minute the agent arms the RTC alarm for the next
   scheduled wake (`rtcwake -m no -t`) and powers off cleanly. The trigger is
   a 2-minute window at the sleep time, once per day, and a box with under
   10 min uptime skips it — so a screen someone switches on during the sleep
   window **stays up until the next scheduled sleep**. Fallback ladder: RTC
   arm fails (or unsupported) but wake-on-LAN is armed → power off anyway and
   rely on the manager's WoL relay; neither → display-off sleep
   (`systemctl stop kiosk-display`, resumed at the stored wake time, or
   immediately if the schedule is removed). The agent probes its wake
   capabilities at startup (`rtcwake --dry-run`, wired NIC MAC, `ethtool`
   Wake-on `g` — re-asserted every tick, since interface resets restore the
   driver default, the same lesson the WiFi powersave watchdog learned) and
   reports them on every poll (`rtcWakeSupported`/`wolMac`/`wolEnabled`,
   additive). The manager relays wakes by queueing `wol:<12-hex-mac>` to an
   awake sibling on the asleep screen's subnet; the sibling broadcasts three
   magic packets (python, UDP :9) — magic packets don't cross VLANs, which is
   why the server never sends them itself.

**Instant sync:** the manager SSHes in as the kiosk user with that restricted
key; the forced command runs `kiosk-trigger`, which sends SIGUSR1 to the
agent. The signal interrupts the sleep between ticks, so a change made in the
manager UI lands in ~1–2 s instead of up to 15. A signal that arrives while a
tick is running skips the next sleep entirely, so back-to-back pushes are
never swallowed.

**Self-update** (`update-agent` command): the agent acks, then re-runs
`kiosk-setup.sh` from the repo inside a detached transient unit
(`systemd-run --unit=kiosk-agent-update`) so the installer's own
`systemctl restart kiosk-agent` doesn't kill the update mid-run. The installer
preserves `agent.env` (so no re-registration), skips apt entirely when all
packages are already present (works at sites whose firewalls block the Ubuntu
mirrors), reinstalls all `agent/*` files and restarts the services. Every run
logs to `/var/log/kiosk-setup.log`.

## 6. Wire contract (manager ↔ agent)

- Agent API routes (`/api/agent/*`) and the config JSON shape must stay
  backward-compatible: **new fields are additive and optional**, and old
  agents must be able to ignore them (e.g. per-tile `subtype`, `wifiSsid`).
  Never rename or repurpose an existing field — screens update on their own
  schedule and any mix of versions can be in the field at once.
- Screen and command ids are opaque GUIDs for the same reason.
- The agent treats every payload defensively: JSON validated before use,
  numeric fields sanitized, config bounds checked.

## 7. WiFi

Three pieces, all independent of the display:

- **`kiosk-apply-wifi SSID [PSK]`** writes
  `/etc/netplan/90-kiosk-wifi.yaml` with DHCP `route-metric: 4096`. Wired
  DHCP routes get networkd's default metric 1024, so the kernel prefers the
  cable whenever it's connected and fails over to WiFi (and back) purely via
  routing — no carrier-watching daemon. WiFi-only screens simply use WiFi as
  their main path. Idempotent: if the generated YAML is unchanged nothing is
  touched (`netplan apply` blips interfaces, so it only runs on change). The
  fleet-wide SSID/password is distributed by the manager and applied by the
  agent on every config sync; an empty SSID clears the config.
- **wait-online `--any`** drop-in: with wired + WiFi both managed, boot must
  proceed when *either* is up — the default waits for all interfaces and an
  unplugged cable would stall boot ~2 minutes.
- **`kiosk-wifi-watchdog.service`** — WiFi husbandry, every 60 s:
  - Re-asserts `iw dev <wlan> set power_save off` on every wireless
    interface. Power saving causes latency spikes and micro-disconnects that
    stall RTSP (the classic "WiFi screen keeps losing tiles, wired screen is
    fine" pattern). Deliberately not a run-once: the setting reverts to the
    driver default whenever the interface resets — which is exactly what
    happens on the flaky links this exists to fix.
  - When the **default route runs over WiFi**, pings the gateway and
    escalates on sustained loss, once per outage episode:
    **3 min** → interface bounce (down/up: fresh association + DHCP);
    **6 min** → WiFi driver module reload — this is the part of a reboot
    that actually fixes a NIC whose firmware has degraded after hours of
    sustained streaming (the "flawless for hours, then gradually worse until
    nothing, reboot cures it" pattern, notorious on Intel iwlwifi);
    **15 min** → reboot as a last resort, guarded so it can never loop:
    uptime must exceed 30 min and at most one watchdog reboot per 6 h
    (persistent stamp survives the reboot). A dead AP therefore gets exactly
    one reboot attempt, then the watchdog just keeps logging.
  - On a screen whose default route is wired, the health check is a silent
    no-op — streams don't depend on WiFi there.

## 8. Security model

- The **enroll token** is only good for registering; each screen then holds
  its own bearer token (600-perm file, root only).
- The **manager's SSH key** on a screen is `restrict`-ed to one forced
  command, and the sudoers rule allows the kiosk user exactly
  `/usr/local/sbin/kiosk-trigger` as root — the manager can wake the agent
  and nothing else. The rule is `visudo -cf`-validated before install.
- **NVR credentials** live in `config.json` (root:kiosk 640) and in mpv's
  command line on the box (visible to local users in `ps`; the box is
  single-purpose and the NVR user should be a least-privilege live-view
  account).
- `kiosk-update-ssh-keys` only ever rewrites its own marker block and refuses
  to apply an empty key list, so a manager bug can't lock everyone out.
- `cams.sh` runs as the unprivileged kiosk user; the agent (root) never
  executes manager-supplied strings — commands are a fixed enum.

## 9. Ops quick reference

```bash
journalctl -u kiosk-agent -f        # manager sync, config versions, commands
journalctl -t kiosk-cams -f         # per-tile player/watchdog activity
journalctl -u kiosk-agent-update    # last remote self-update run
cat /var/log/kiosk-setup.log        # last installer run, full detail
systemctl status kiosk-display kiosk-agent kiosk-wifi-watchdog
journalctl -u kiosk-wifi-watchdog     # link-loss episodes and recovery escalations
grep AGENT_VERSION= /usr/local/sbin/kiosk-agent
iw dev <wlan> get power_save        # should be: off (interface name is NOT wlan0 -
                                    #   predictable naming, e.g. wlp2s0; find it with: iw dev)
cat /etc/kiosk/config.json | jq .   # what the screen thinks it should show
KIOSK_DRYRUN=1 /etc/kiosk/cams.sh   # print the xrandr/mpv commands without running them
```

**BIOS prerequisites for the power schedule** (found the hard way on
ejt-mb-wk-106, 2026-10-06: sleep worked, every wake path was dead): in S5 with
Intel's deep-sleep setting on, the NUC powers down both the RTC alarm circuit
and the NIC, so neither the armed RTC wake nor WoL magic packets can reach it
— only the power button. On each screen, in BIOS setup (F2) under Power →
Secondary Power Settings:

- **Deep S4/S5 / Deep Sleep: Disabled**
- **Wake on LAN from S4/S5: Power On – Normal Boot**

Quick tell while a box is off: a dark Ethernet link LED means the NIC is
unpowered and WoL cannot work. The agent's capability probe cannot see these
BIOS settings — `rtcwake --dry-run` succeeds and `ethtool` reports `wol g`
even when deep sleep will defeat both.

Camera-side settings that matter:

- **H.264 only** — the Intel i965 VAAPI driver cannot hardware-decode H.265.
- **Keyframe (I-frame) interval 1–2× the frame rate** (e.g. 25–50 at 25 fps):
  after any glitch the picture can only fully clean up at a keyframe, so long
  intervals make every glitch linger.
- Substreams for grid cells (a 6×6 wall of main streams is a decode wall, and
  the cells are small anyway); main stream for single-camera screens or
  feature tiles.
- Mixed resolutions are fine — every tile scales to its cell.

## 10. Version history (the short story)

| Version | Change |
|---|---|
| ≤1.7 | single mpv compositing the wall via a filter graph |
| 1.8 | per-tile main/substream selection |
| 1.9 | one mpv per tile; first watchdog. **Bug:** `err_detect +explode` could wedge a player into a permanent black window the watchdog didn't recognise |
| 2.0 | watchdog covers black windows; explode dropped; stale-pid guards |
| 2.1 | WiFi power-save disable (oneshot). **Bug:** v2.0's one-hammer watchdog restarted mid-buffer players on flaky WiFi; oneshot power-save reverted on interface resets |
| 2.2 | failure-aware policy: in-place reloads, last-frame hold, starvation patience (§4) |
| 2.3 | power-save re-asserted every 60 s |
| 2.4 | power-save unit grew into the WiFi watchdog: gateway health check with bounce → driver reload → guarded reboot escalation, for WiFi stacks that degrade over hours until re-initialised |
| 2.5 | latency governor: tiles >2 s behind live play at 2× until caught up; `cache-secs=10` bounds drift; `no-audio` + `video-latency-hacks` trim fixed delay (tiles used to park 20–40 s behind realtime) |
| 2.6 | relay support: per-tile `url` (the manager's MediaMTX relay — one upstream NVR session per camera) preferred, direct NVR stream as the automatic fallback, seamless in-place switches both ways |
| 2.7 | main-stream degrade: a tile that provably can't sustain its main stream (lag-stuck 120 s or 3-restart churn) drops itself to the same camera's substream in place and retries main every 30 min — main-in-grid softens instead of greying out and starving neighbours |
| 2.8 | power schedule (FB-0176): scheduled sleep via RTC-alarm self-wake, WoL relay through an awake sibling (`wol:` command), display-off fallback; wake capabilities reported on every poll; manual power-on during the sleep window stays up until the next scheduled sleep. **Bug:** schedule times read against the box's own clock — the boxes run UTC, so everything fired an hour late during BST |
| 2.9 | schedule times are wall-clock in `power.timeZone` (default Europe/London) regardless of the box's clock |
